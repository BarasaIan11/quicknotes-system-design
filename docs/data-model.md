# QuickNotes relational data model

QuickNotes uses PostgreSQL. Users own notes and tags. Each note belongs to exactly one user (one-to-many from users to notes). Tags belong to a user, and notes can have many tags while a tag can label many notes; `note_tags` implements that many-to-many relationship. Keeping tags owner-scoped prevents sharing one user's labels with another user's notes.

Types below use PostgreSQL syntax. UUID keys are generated by the application (or `gen_random_uuid()`); timestamps are stored in UTC. Deleting a user cascades to their notes and tags; deleting a note or tag cascades to its link rows.

```sql
CREATE TABLE users (
  id UUID PRIMARY KEY,
  email VARCHAR(320) NOT NULL UNIQUE,
  password_hash TEXT NOT NULL,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE notes (
  id UUID PRIMARY KEY,
  user_id UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  title VARCHAR(100) NOT NULL,
  body TEXT NOT NULL DEFAULT '',
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  UNIQUE (user_id, id)
);

CREATE TABLE tags (
  id UUID PRIMARY KEY,
  user_id UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  name VARCHAR(50) NOT NULL,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  UNIQUE (user_id, name),
  UNIQUE (user_id, id)
);

CREATE TABLE note_tags (
  note_id UUID NOT NULL REFERENCES notes(id) ON DELETE CASCADE,
  tag_id UUID NOT NULL REFERENCES tags(id) ON DELETE CASCADE,
  user_id UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  PRIMARY KEY (note_id, tag_id),
  FOREIGN KEY (user_id, note_id) REFERENCES notes(user_id, id) ON DELETE CASCADE,
  FOREIGN KEY (user_id, tag_id) REFERENCES tags(user_id, id) ON DELETE CASCADE
);
```

The composite foreign keys on `note_tags` require a note and tag to belong to the same user. The `(user_id, id)` unique keys make those ownership-safe references valid.

PostgreSQL does not automatically index referencing foreign-key columns. These indexes support the common per-user timeline, the tag reverse lookup, and account cleanup:

```sql
CREATE INDEX notes_user_updated_idx ON notes (user_id, updated_at DESC, id DESC);
CREATE INDEX note_tags_tag_note_idx ON note_tags (tag_id, note_id);
CREATE INDEX tags_user_name_idx ON tags (user_id, name);
```

The first index makes paginated note listing efficient; the reverse link index supports finding notes by tag. The unique constraints already index user email, user/tag name, and note/tag pairs.

## Example queries

List a user's newest notes:

```sql
SELECT id, title, body, created_at, updated_at
FROM notes
WHERE user_id = $1
ORDER BY updated_at DESC, id DESC
LIMIT 50;
```

Find notes with a particular tag (JOIN across all four entities):

```sql
SELECT n.id, n.title, n.body, t.name AS tag
FROM users u
JOIN notes n ON n.user_id = u.id
JOIN note_tags nt ON nt.note_id = n.id AND nt.user_id = u.id
JOIN tags t ON t.id = nt.tag_id AND t.user_id = u.id
WHERE u.id = $1 AND t.name = $2
ORDER BY n.updated_at DESC;
```

Add a tag to one of the caller's notes, safely ignoring a repeated request:

```sql
INSERT INTO note_tags (note_id, tag_id, user_id)
SELECT n.id, t.id, n.user_id
FROM notes n JOIN tags t ON t.id = $2 AND t.user_id = n.user_id
WHERE n.id = $1 AND n.user_id = $3
ON CONFLICT (note_id, tag_id) DO NOTHING;
```

## SQL or NoSQL?

SQL is the right starting point because ownership, uniqueness, and the note/tag many-to-many relationship need transactional guarantees and joins. PostgreSQL provides mature indexing, constraints, and read replicas, while the expected workload is well served by indexed relational queries. If usage later shows a specific access pattern cannot meet its latency target, a cache or derived search index can be added without giving up the relational source of truth.
